# Нативная VLIW-ISA Crusoe TM5x00 (по образу CMS 4.4.03)

Всё ниже проверено на распакованном `cms4.4.03raptor.cru` (SoftPaq SP23689) и реализовано в
`tools/crusoe_isa.py`, `tools/crusoe_dis.py`, `tools/crusoe_asm.py`. Источники сверки:
статья «Crusoe Exposed» part 1/2 (Real World Tech, 2004; её дизассемблер и таблицы опкодов
утеряны, ссылки 404), Crusoe BIOS Programmer's Guide / MSR / Software Optimization Guide
(Transmeta, 2001–2002, лежат на datasheets.chipdb.org).

Уровень уверенности: **[точно]** — сходится до единицы с независимой статистикой или
проверено разбором; **[гипотеза]** — объясняет данные, но не доказано.

## Адресация и область кода

- Образ грузится по CMS-адресу `0x8e000`; адрес = смещение в образе + 0x8e000. Все адреса в
  листингах — в этом пространстве (совпадает с нумерацией статьи).
- Код: `0x8e000..0x1823f0` (1 000 432 байт). Данные: `0x1823f0..0x1b2261`. Выше — BSS, стек,
  кэш трансляций (адреса вида `0x22edxx` в коде — BSS).
- Порядок байт и слов — little-endian. **[точно]**

## Молекулы (связки)

Молекула = 64 или 128 бит = 2 или 4 атома по 32 бита (`w0..w3`). Формат задаёт **второе слово**:

| `w1[30:29]` | длина | слоты `w0, w1, w2, w3` | примечание |
|---|---|---|---|
| `00` | 128 | IMM32/BRU, ALU0, ALU1, LSU | `w1[31]`: 0 → `w0`=IMM32, 1 → `w0`=BRU |
| `01` | 64 | ALU1, LSU | |
| `10` | 64 | ALU1, ALU0 | если опкод ALU0 — imm32-форма, то `w0`=IMM32 |
| `11` | 64 | BRU, ALU0 | |

**[точно]**: линейный разбор всей области кода по этому правилу даёт ровно ту перепись связок,
что опубликована в «Crusoe Exposed» для того же образа: 101 757 связок, из них
LSU|ALU1 25 401, ALU0|ALU1 31 625, ALU0|IMM 5 409, ALU0|BRU 16 025, 128-битных с IMM 13 386,
с BRU 9 911 (78 460 × 64 + 23 297 × 128 бит = 250 108 слов — весь код).

Почему формат во втором слове: `w0` может быть сырой 32-битной константой, значит признак
формата не может лежать в нём. Цели переходов выровнены на 8 байт, так что 64-битная
молекула может начинаться с любого 8-байтного адреса.

Между функциями встречаются слова-заполнители (`00000000`); линейный разбор на них
рассинхронизируется. Дизассемблер пересинхронизируется по целям переходов и печатает такие
слова как `.word` (50 штук на весь образ).

Внутри молекулы атомы исполняются параллельно и читают **старые** значения регистров
(пример: `link = r27; r27 = load(...)` в одной молекуле). **[точно по коду пролога/эпилога]**

## Атом ALU / LSU

    31  29 28        20 19    14 13     8 7          2 1  0
    [ top ][  opcode 9 ][  rd    ][  rs1   ][ rs2 / imm8 ...  ]

- `opcode` — 9 бит, одно пространство для всех блоков (так и в статье). **[точно]**
- Форма операнда — в младших битах опкода **[точно для известных опкодов]**:
  `xxxxxx000` — регистр-регистр, `rs2 = [7:2]`, `[1:0]` — доп. поле (обычно `11`; CMS сам
  печатает суффиксы `.00 .01 .10 .11`);
  `xxxxxx011` — `imm8 = [7:0]` со знаком;
  `11xxxx011` — 32-битная константа из IMM-слова молекулы (`addil 0x183`, `andil 0x1a3`,
  `oril 0x1bb`, `cmpil.c 0x1f3`).
- `top [31:29]`:
  - в `w1` биты `[30:29]` — формат молекулы, `[31]` — свободный флаг в 64-битных молекулах
    (у дизассемблера суффикс `.cm`; **[гипотеза]** бит commit — статья пишет, что у молекулы
    есть бит commit, фиксирующий теневые регистры);
  - в ALU1 биты `[30:29]` — «type select»: `00` — целочисленный атом, иначе отдельное
    пространство опкодов (FP/MMX/спецрегистры), печатается как `tN.opXXX` **[точно]**
    (статья: «ALU1 type select bits other than 00 → FP/MMX»);
  - в LSU `w3` 128-битной молекулы `[31]` — тот же флаг, `[30:29]` почти всегда 0.

### Известные опкоды

| опкод | имя | откуда |
|---|---|---|
| `100` / `103` / `183` | add / addi / addil | статья + форма |
| `138` / `13b` / `1bb` | or (`mov` при `%zero`) / ori / oril | статья |
| `120` / `123` / `1a3` | and / andi / andil | таблица автора статьи |
| `170` / `173` / `1f3` | sub.c / subi.c / subil.c (со `%sink` = сравнение; 302 раза пишут в настоящий регистр) | таблица автора + подсчёт |
| `068` / `118` | movlink? / oprr? (без type) | таблица автора, с «?» |
| `020` | cmp.and (комбинирование условий, как crand в PowerPC) | статья |
| `093` | slli (сдвиги — только ALU1) | статья |
| `14b` | nop (точное слово `0x14b00000`) | статья + статистика |
| `03b` | nop.lsu (точное слово `0x03b00600`) | статья + статистика |
| `050` | ld `rd, [rs2], m=rs1` — `[13:8]` не регистр, а режим (4 / 20 / …) | статья + статистика |
| `044` | st `[rs2], rs1, m=rd` — `[19:14]` режим (12 / 28 / …) | статья + статистика |
| `053` | ldi `rd, rs1, imm8` — imm8-форма `ld`: слот локального массива; RDMSR 0x174/0x175/0x176 = `ldi %r0, %r21, 50/51/52` (копии x86-MSR в LDM) | разбор, **[гипотеза]** по имени |
| `098` / `09b` | srl / srli | **[гипотеза]**: соседи `sll 090` / `slli 093` |
| ALU1 `t2.xx1100000` | mfsr / mfb1 / mfb2 / mfb3: `rd = bank[rs1]` (`rs2` = 0). Биты `[8:7]` = номер банка | гистограмма автора + поля |
| ALU1 `t2.xx1101000` | mtsr / mtb1 / mtb2 / mtb3: `bank[rs1] = rs2` (`rd` = 0). `br.prep` статьи = `mtsr %link` | то же |
| ALU1 `t2.040/048/050/058` | без операндов (все поля 0) — управляющие атомы **[гипотеза: барьеры]** | поля |

Остальные опкоды печатаются как `opXXX` (гистограмма по блокам — `crusoe_dis.py --stats`
и раздел ниже). Мнемоник внутри CMS нет: его встроенный печатальщик атомов для неизвестного
опкода выводит `?OP0%o?`.

Режим LSU: в коде есть два класса обращений — к физической памяти CMS и через x86-TLB
(статья, p8); поле режима, вероятно, кодирует размер и класс (биты 2–4) **[гипотеза]**.

## Атом BRU (переход)

    31  29 28  25 24  23  22                         0
    [kind ][ cc  ][x ][i][   target >> 3 (абсолютный)  ]

- `kind 100` — безусловный; `cc[0]` = L → запись адреса возврата в `%link` (call). **[точно]**
- `kind 101` — условный по флагам, `cc` в порядке x86 Jcc: o no b nb e ne be nbe s ns p np
  l nl le nle (тот же порядок, что в таблице строк `#o, #no, …` внутри CMS). **[точно]**
  Пример: `cmpil.c eax, 0x80000006` + `brc.nbe` = «если eax > 0x80000006 (беззнаково)».
- `kind 111` — условный по второму набору условий **[гипотеза]**; печатается `brc2.<cc>`.
- `[22:0]` — цель / 8, абсолютный адрес → CMS не больше 64 МБ (как в статье). **[точно]**
- `[23] = 1` — косвенный переход на регистр, подготовленный `br.prep` (почти всегда `%link`);
  младшие биты (`0x74..0x7e`, `0x60..0x6a`) — не номер регистра, а подсказка/вариант
  **[точно, что не регистр: проверено по 1009 косвенным переходам]**.

## Регистры

Имена восстановлены из таблицы строк встроенного печатальщика CMS (`0xfad80..0xfb173`,
строки лежат подряд в обратном порядке):

| пространство | номера | имена |
|---|---|---|
| GPR | 0–63 | `%r0..%r61`, `%sink` (62, приёмник-«чёрная дыра»), `%zero` (63) |
| SPR | 0–63 | `%weflags` 0, `%aeflags` 1, `%pci_status` 8, `%selector0..7` 16–23, `%limit0..7` 24–31, `%fl_stack_eip` 32, `%fl_ctx` 33, `%fl_eip` 35, `%link` 58, `%from` 59 |
| FPR | 0–31 | `%f0..%f31` (80-битные) |
| ещё два класса | | `X32..X62` с `%acpc` на 59-м; `0x00..0x77` (64 штуки) |

Соглашения CMS (статья + разбор): `%r0..%r3` = x86 `eax, ecx, edx, ebx`; `%r47` — стек CMS;
нижние 48 GPR имеют теневые копии (откат при исключении). CMS скомпилирован из C
(модифицированный gcc) плюс ручной VLIW-ассемблер.

## Инструменты

    python3 tools/crusoe_dis.py IMAGE [START [END]]      # листинг
    python3 tools/crusoe_dis.py IMAGE START END -c       # псевдо-C («декомпилятор»)
    python3 tools/crusoe_dis.py IMAGE --stats            # перепись молекул
    python3 tools/crusoe_asm.py SRC.s -o OUT.bin --org ADDR
    python3 tools/crusoe_asm.py SRC.s --patch IMAGE -o NEW.image
    python3 tools/crusoe_asm.py --selftest IMAGE         # dis → asm по всему CMS

`--selftest` пересобирает весь код CMS из листинга: **0 расхождений на 250 108 словах**.
Формат листинга и ассемблера один и тот же, так что листинг можно править и собирать
обратно. Пример ручного кода — `examples/example.s`.

## Сверка с дизассемблером автора «Crusoe Exposed»

Приложения к статье нашлись в Wayback Machine: `CrusoeReport-Part2-Disasm.cpp` (таблица
опкодов, разбор полей) и `CrusoeReport-Part2-Samples.S` (размеченные листинги; копия в
`third_party/`). Результат сверки:

- **Формат молекул совпадает полностью**: у автора тип = биты 61–62 первого 64-битного
  слова = `w1[30:29]`, те же слоты и тот же признак imm32 (`11xxxx011`, только ALU0).
- **Размеченные примеры**: 37 из 38 молекул совпали слово в слово. В 38-й (`0xa6810`) автор
  не показал слово BRU `ac014d17` (условный переход на `0xa68b8`), хотя оно есть в образе.
- **Поля ALU/LSU/BRU** совпадают (`[1:0]` у автора тоже «unknown»).
- Бит `w1[31]` автор называет **commit**, в том числе в 128-битной связке. Там же этот бит
  выбирает IMM или BRU в `w0`, а commit автор берёт из `w3[31]`. Это совпадает с моим `.cm`,
  но и у автора остаётся предположением.
- **Расхождения, где прав разбор по данным**:
  - вызов у автора — `cond` бит 1, но у безусловных переходов в образе `cond` равен только
    0 (5409) или 1 (5464). Бит 1 не встречается, так что L = бит 0, и именно цели с `cond=1`
    начинаются с пролога функции (`sp -= N`);
  - косвенный переход автор читает как регистр в `[6:1]`, но перед каждым таким переходом
    `br.prep` пишет в `%link`, какими бы ни были эти биты, так что это не номер регистра;
  - имена условий у автора `lt/ge/le/gt` для кодов 2, 3, 6, 7 на деле беззнаковые
    (`b/nb/be/nbe`), например `eax > 0x80000006` для листов CPUID.
- **Гистограммы опкодов** (`CrusoeReport-Part2-histogram.txt`, присланы пользователем)
  совпадают с `crusoe_dis.py --histogram` во всех таблицах: ALU0, ALU1 по типам 0–7, LSU
  (итоги 76 356 / 80 323 / 48 698). Из них же видна структура типа 2: пары опкодов
  `x0/x8` в четырёх банках — пересылки между GPR и банками регистров (банк 0 = спецрегистры).
  Банк выбирают биты `[8:7]`, направление — бит 3. Чтение (`x0`) всегда пишет `rd` при
  `rs2 = 0`, запись (`x8`) — наоборот.
- Функцию `0xa6798` автор назвал `read_msr`, а это обработчик **CPUID** (настоящий RDMSR —
  `f_a7590`). Сам автор в комментариях пишет про «cpuid data».

## Что не закрыто

- Имена ~200 опкодов (`opXXX`), в том числе FP/MMX (`tN.*`), и точная семантика поля `[1:0]`.
- Смысл бита `.cm` (commit — гипотеза) и `kind 111` у переходов.
- Режимы LSU (`m=`).
Путь закрытия: сопоставлять обработчики x86-инструкций в интерпретаторе с их x86-семантикой
(каждый реализует одну известную операцию) — так именуются опкоды по одному.
