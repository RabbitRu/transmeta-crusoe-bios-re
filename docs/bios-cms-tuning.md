# Можно ли ускорить CMS настройками BIOS, не меняя сам CMS

Короткий ответ: **да, но рычаги — это не «настройки транслятора», а то, что CMS получает от
BIOS/ОС через MSR и регистры встроенного северного моста.** Кэш трансляций, пороги
перетрансляции и т.п. снаружи не настраиваются: размер CMS-памяти фиксирован (16 МБ, `TOM`
только для чтения), документированных параметров транслятора нет ни в BIOS Guide, ни в MSR.

Все регистры ниже CMS эмулирует сам (северный мост «живёт» внутри CMS, отсюда строки
`NB Read/Write` в образе), поэтому их можно менять **и из BIOS, и из работающей ОС** — патч
BIOS для экспериментов не нужен. Источник: Transmeta *BIOS Programmer's Guide* (06.2002),
*Model-Specific Registers* (04.2002), *Software Optimization Guide* (08.2001).

## Рычаги, по убыванию пользы

| # | что | где | эффект | риск |
|---|---|---|---|---|
| 1 | Окно LongRun 100/100 + «performance mode» | MSR `0x80868010` = EDX 100 / EAX 100; MSR `0x80868011` бит 0 = 1 | максимальная частота всё время, без провалов на переключение уровней | нагрев, батарея |
| 2 | Не ограничивать LongRun термо-управлением | PCI 00:00.0 `A8h` `LR_ATM`: бит 4 `ATM_EN` = 0 (поле 3:1 — целевое снижение мощности до 75 %) | снимает искусственный потолок частоты | перегрев — следить за температурой |
| 3 | Выключить энергосбережение памяти | PCI 00:00.0 `7Bh` `PM_CR2_OPT`: бит 0 `PSM_EN` = 0 | убирает **+1 такт на каждое обращение к памяти** (CMS и система; по умолчанию 0, но OEM может включить) | чуть выше потребление |
| 4 | `PERF_CTRL` = 0 после загрузки | PCI 00:00.0 `A9h` бит 0 | бит 1 = «оптимизации под загрузку Windows XP»; во время обычной работы Transmeta требует 0. Начальное значение берётся из `winxp_flags` OCT — если OEM оставил 1, приложения теряют | нет |
| 5 | Меньше SMI | BIOS Setup: legacy USB emulation, APM-опрос, «SMI-hotkeys» | SMM-код и real-mode CMS исполняет плохо (Optimization Guide); каждый SMI сбрасывает выгоду трансляций | потеря USB-клавиатуры в DOS |
| 6 | Тайминги памяти через SPD-регистры | PCI 00:00.1 `60h..A4h` (`Bn_TIMING_CL1/2`, `Bn_TIMING_RAS`, `Bn_REFRESH`, `Bn_MISC`) + `SD_CTRL 40h` commit | BIOS переписывает туда SPD модуля, а **тайминги вычисляет CMS** (`DI warning: overclocking (tCK…)`). «Оптимистичный» SPD → более агрессивные тайминги. Реальные значения: `SD_TIF0/1` (00:00.0 `80h`), MSR `0x80868031/34` | **высокий**: нестабильность памяти, в т.ч. CMS-памяти → зависание. Только с recovery-путём |
| 7 | Арбитр PCI | PCI 00:00.0 `ACh` `PCI_ARB_CTRL` (8 слотов по 3 бита; по умолчанию `002266A6h` или из OCT) | приоритет процессора над bus-master (видео/IDE) — заметно на интегрированной графике/UMA | артефакты/просадки DMA |
| 8 | Кэшируемость теневых ROM | PCI 00:00.0 `59h..5Fh` `PAB*` | быстрее вызовы VGA BIOS / int 10h (DOS-игры, загрузка) | мелкий |
| 9 | CPUID: семейство 6 и маска флагов | MSR `0x80860000` `CPUID_TFMS` (R/W), `0x80860004` `CPUID_MASK` | не ускоряет CMS, но программы, выбирающие код по `family`, могут взять ветку i686 (CMOV) | старые драйверы, ждущие от family 6 MTRR/MCA |

Что **не** работает из BIOS: размер кэша трансляций, агрессивность оптимизатора, пороги
горячего кода, отключение самопроверок — это внутренние переменные CMS. Их можно менять только
патчем CMS (в RAM или во флеше) — этим и полезны дизассемблер и ассемблер.

## Пограничный случай: OEM Configuration Table

OCT — отдельная область флеша CMS (№ 3 в протоколе `0x80868000`, см. `docs/cms-architecture.md`).
В ней заданы `winxp_flags`, `pci_arb_ctrl_initial_value`, `initial_pci_latency_timer`,
`OEMOPT`, и, судя по строкам CMS и отсутствию таблиц МГц/мВ в образе, — **уровни LongRun и
делители памяти**. Это «BIOS-уровень без замены CMS» в чистом виде: если запись OCT не
требует подписи, через неё можно менять рабочие точки (разгон) и умолчания, не трогая сам
CMS. Порядок:

1. `python3 tools/cms_flash_read.py --sizes` — размеры областей (безопасно, только rdmsr).
2. `--read 3 oct.bin --i-understand` — снять OCT; заодно снять обе копии CMS (области 1/2) как
   резервную копию перед любыми экспериментами.
3. Разобрать поля OCT (заголовок, версия по `+0x428`, таблица уровней) — следующий шаг.
4. Разобрать ветку записи `L_a6bf0 → f_fd710` в CMS: есть ли проверка подписи для OCT.

## Как проверить на своих машинах

    sudo modprobe msr cpuid
    sudo python3 tools/crusoe_probe.py > probe-c1mw.txt

Зонд только читает: CPUID, MSR Transmeta, таблицу LongRun со всеми делителями и словами
таймингов, размеры областей флеша, регистры 00:00.0/00:00.1. По нему сразу видно, какие из
пунктов 1–4 у конкретного BIOS выставлены неоптимально.

Применить пункты 1–4 на время сеанса (msr-tools и pciutils):

    sudo wrmsr 0x80868010 0x0000006400000064
    sudo wrmsr 0x80868011 1
    sudo setpci -s 00:00.0 a9.b=00:01
    sudo setpci -s 00:00.0 7b.b=00:01
    sudo setpci -s 00:00.0 a8.b=00:10

(`setpci reg=value:mask` меняет только биты маски.) Закрепить — через скрипт загрузки ОС или,
позже, патчем BIOS Sony (известные места: POST-замер частоты `B1`+0x3467 / `B2`+0x233B и блок
OCT `B2`+0xA1B5 в R0248 — см. `docs/bios-sony.md`).

Ожидаемый порядок выигрыша: пункты 1–2 дают десятки процентов, если LongRun сейчас держит
средние уровни; 3–5 — единицы процентов в среднем, но заметнее на памяти и в играх; 6 —
до ~10 % на память ценой стабильности. Цифры — оценка, мерить бенчмарками до/после
(повторный прогон, чтобы исключить разогрев трансляций).
